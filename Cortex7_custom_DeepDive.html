Iceberg materialization and incremental load cost in Cortex v7

A production SAP deployment publishes ~50 Cortex data products as managed Apache Iceberg tables in Cloud Storage, and cut incremental MERGE cost by up to 22×. This document walks through each change, the SQL it emits, and the failure modes we hit along the way.

Resulting architecture

The fork does not change Cortex's design — it changes the storage format at the final hop. The data product layer stops being native BigQuery storage and becomes Iceberg in Cloud Storage, so engines outside BigQuery can read the same files.

i Why managed Iceberg rather than native tables

A native BigQuery table is readable only by BigQuery. With managed Iceberg (BigLake), the Parquet files and Iceberg metadata live in a Cloud Storage bucket in an open format — BigQuery continues to read and write normally, and other engines read the same files with no copy and no export step.

Change 1 · the engine

The Iceberg helper

All Iceberg materialization runs through one new file, src/dataform_includes/iceberg_helper.js (397 lines). It exists for a specific and non-obvious reason.

! The problem it solves

Dataform's publish() does not emit WITH CONNECTION … OPTIONS(table_format='ICEBERG') from a bigquery.iceberg config block. It creates a native BigQuery table, silently — no error, no warning. The configuration looks correct and the output is wrong.

The workaround is to write the Iceberg DDL by hand, through operate() instead of publish(). That trade is expensive: leaving the publish() path forfeits everything Dataform does underneath — column descriptions, metadata application, onSchemaChange. Much of the rest of this document is rebuilding those losses.

product definition — beforeBaseline
publish(moduleContext.moduleId + "_" + tableConfig.tableName,
        publishConfig).query(
  (ctx) => `
SELECT … FROM …
`
);
product definition — afterFork
const iceberg_helper = require("includes/iceberg_helper.js");

iceberg_helper.publishProduct(
  moduleContext.moduleId + "_" + tableConfig.tableName,
  publishConfig,
  tableConfig,
  (ctx) => `
SELECT … FROM …
`
);

✓ Backward compatible by construction

If a product does not declare the bigquery.iceberg block, the helper calls native publish() and nothing changes. Adoption is per-product — a repository can run Iceberg and native tables side by side.

Statements it emits

Two paths, selected by the product's materializationType:

table Full refresh

  • CREATE OR REPLACE TABLE … PARTITION BY … CLUSTER BY … WITH CONNECTION … OPTIONS(…)
  • ALTER TABLE applying column descriptions
  • EXPORT TABLE METADATA

incremental Delta load

  • CREATE TABLE IF NOT EXISTS … AS SELECT … WHERE FALSE — creates empty on first run
  • ALTER TABLE applying descriptions
  • BEGIN DECLARE _watermark … MERGE … END;
  • EXPORT TABLE METADATA

! Separate statements, not an IF/ELSE script

BigQuery validates the entire script before executing. A MERGE referencing a table that does not yet exist fails validation even inside an ELSE that would never run. Hence the separate CREATE TABLE IF NOT EXISTS: it creates on the first run and becomes a no-op afterward.

! DDL clause order is mandatory

PARTITION BY → CLUSTER BY → WITH CONNECTION → OPTIONS. Any other order is a syntax error on the Iceberg path. Native BigQuery is more permissive, which makes this easy to get wrong.

Change 2 · metadata

Recovering column descriptions

The first of the losses caused by trading publish() for operate() — and it went unnoticed for months.

! Iceberg products had no descriptions at all

On the native path, Dataform applies publishConfig.columns through the API (tables.patch). Because the helper uses operate(), that mechanism never ran: annotations stayed in the repository and the BigQuery tables reached the catalog with no documentation whatsoever.

CREATE … AS SELECT cannot annotate columns, so the only route is an ALTER after creation. The helper builds a single statement covering every column — validated at 491 columns in one statement.

iceberg_helper.js — buildDescriptionsSql()Fork
BEGIN
ALTER TABLE `project.dataset.table`
  ALTER COLUMN `client_mandt` SET OPTIONS(description='SAP client'),
  ALTER COLUMN `company_code` SET OPTIONS(description='Company code');
EXCEPTION WHEN ERROR THEN
  SELECT CONCAT('[iceberg_helper] column descriptions skipped: ', @@error.message);
END;

✓ Not create-time

Works on an existing table. Changing a description does not require rebuilding — unlike schema, key, partitioning, or clustering.

! The handler hides failures by design

Descriptions are metadata and must never fail an hourly load. But if a column is missing from the table, the whole ALTER becomes a silent no-op and the job stays green. Grep the run log for skipped:.

Escaping is mandatory and not a detail: SAP annotations contain apostrophes (Trading Partner's Business Area) and line breaks, and either one breaks the SQL literal — taking down the entire product's DDL.

Change 3 · physical layout

Partitioning and clustering that actually apply

Where layout settings actually arrive

cortex-build reads partitionDetails and clusterDetails from the YAML, translates them into Dataform's format, and delivers them in publishConfig.bigquery. The original keys disappear along the way.

configuration flowcortex-build behavior
table_settings.default.yaml
        ↓  (cortex-build TRANSLATES and DISCARDS the original keys)
publishConfig.bigquery.partitionBy   = "DATE(column)"
publishConfig.bigquery.clusterBy     = ["col1", "col2", …]
publishConfig.columns                = {column: description}
        ↓
iceberg_helper.publishProduct(…)

// tableConfig reaches the helper carrying only:
// ["tableName","tags","materializationType","bigquery","description","columns"]

! Reading tableConfig.partitionDetails returns undefined

Silently. The helper falls through and nothing happens — the table is rebuilt without partitioning while the YAML looks correct. Worse: keys that cortex-build does not recognize pass YAML validation and are discarded. Dead configuration is worse than absent configuration, because it reads as working.

The DATE(col) correction

cortex-build assembles partitionBy without inspecting types: a column plus partitionType: DATE becomes DATE(column). When the column is already DATE — the case for every SAP date field — BigQuery rejects the CREATE, because DATE() accepts only TIMESTAMP or DATETIME.

iceberg_helper.js — selective unwrappingFork
// Unwraps DATE(col) → col when the argument is a simple identifier.
// Leaves DATE_TRUNC(...) and TIMESTAMP_TRUNC(...) intact.
const unwrapped = rawPartition.replace(/^DATE\(\s*([A-Za-z0-9_]+)\s*\)$/, "$1");

Clustering from the YAML, not from the key

The helper prefers publishConfig.bigquery.clusterBy and falls back to the unique key only when the YAML declares nothing. The difference is concrete: Cortex keys begin with columns that are constant in many landscapes — client and ledger — and BigQuery allows only four clustering columns.

i The partition exists, but not where you would look for it

INFORMATION_SCHEMA.TABLES.ddl does not render the PARTITION BY clause for Iceberg tables — it shows only CLUSTER BY. That led to the wrong conclusion that partitioning did not persist, and the incorrect comment in the code blocked the implementation for months.

The reliable source is the BigQuery UI, Details tab: it should read "Partitioned by DAY" and name the field.

Change 4 · load cost

Watermark materialized as a script variable

The first of three cost levers, and the most transferable: it applies to every incremental Cortex data product, in any deployment.

Cortex's incremental filter compares the source recordstamp against the maximum already loaded into the target. Because that cutoff comes from a correlated subquery, BigQuery does not know the value at planning time and cannot prune partitions — it reads almost the entire source on every run.

filter — beforeNo pruning
MERGE target T
USING (
  SELECT … FROM source
  WHERE recordstamp >= (
    SELECT MAX(source_last_updated_at)
    FROM target
  )
) S ON …
filter — afterPrunes partitions
BEGIN
  DECLARE _watermark TIMESTAMP DEFAULT (
    SELECT MAX(source_last_updated_at) FROM target
  );
  MERGE target T
  USING (
    SELECT … FROM source
    WHERE recordstamp >= _watermark
  ) S ON …
END;

Measured in production, same delta, same result:

Filter formBytes readReading
Literal >= TIMESTAMP('…')22 MBtheoretical best
Correlated subquery5.5 GB250× more expensive
Script variable (DECLARE)18.6 MBmatches the literal

✓ No semantic change, no rebuild

The cutoff value is identical — simply evaluated once, before the MERGE, rather than inside it. And because it changes only the filter, it requires no DROP: it takes effect on the next run.

! The substitution is textual

The helper looks for the subquery in the exact form generated by incremental.getFilter and swaps it for the variable. If the text does not match — different indentation or quoting — behavior stays correct but the saving disappears. A safe fallback, but a silent one.

Change 5 · load cost

Partition pruning inside the MERGE

The highest-impact lever — and the only one carrying a correctness precondition that must be verified before adoption.

A key-only ON T.key = S.key never engages the target's partitioning: BigQuery scans the entire table to match keys. On a 370-million-row table that dominates cost. The fix is to give the planner a predicate on the partition column, computing the batch's date bounds into script variables.

iceberg_helper.js — pruning predicate in the ON clauseFork
BEGIN
  DECLARE _watermark TIMESTAMP DEFAULT (…);
  DECLARE _part_min DATE;
  DECLARE _part_max DATE;
  SET (_part_min, _part_max) = (
    SELECT AS STRUCT MIN(`budat`), MAX(`budat`) FROM ( … delta … )
  );

  MERGE target T USING ( … delta … ) S
  ON  T.`budat` BETWEEN COALESCE(_part_min, DATE '0001-01-01')
                    AND COALESCE(_part_max, DATE '9999-12-31')
  AND T.`key` = S.`key` AND …
END;

! Correctness precondition — read before adopting

The range predicate makes the MERGE match only rows whose partition column falls inside the batch bounds. This is safe only if the column is immutable per key. If the value changes between loads, the existing row falls outside the range, the MERGE misses it, and inserts a silent duplicate.

Here it was verified for posting date (immutable after posting): zero divergences across 30 days of CDC and a full fiscal year. That is a verified assumption, not a guarantee — the mitigation is a scheduled uniqueness check, which detects after the fact rather than preventing.

i Why the COALESCE is not optional

If the delta comes back empty, MIN and MAX return NULL and the BETWEEN would never match — the entire delta would be inserted. With an open fallback the predicate is always true and behavior returns to normal: no pruning, but correct.

Three conditions to activate

The helper only builds the predicate when all three hold — any one false leaves the MERGE untouched:

  • the target is partitioned;
  • the partition expression references a single simple column (otherwise it returns null and pruning is disabled);
  • the incremental filter uses a watermark — without it the "delta" is the whole table, and the bounds would span all history.

The third lever stays outside the helper

Source-side pruning could not be automated: the helper receives the product's SELECT as opaque text and has no knowledge of the source tables. It must be written into the product itself, with CTEs filtering each source by the delta's date list. It matters when the filter is evaluated after the joins — the GREATEST(a.recordstamp, b.recordstamp, …) pattern of multi-source products.

i Why the list beat the range

Of ~98,000 delta rows, 90,224 fell on a single day. The rest was a long tail of retroactive adjustments — eight rows from February stretched the range across seven months and cost roughly 250 GB.

! Two measurement traps

Do not measure with COUNT(*). BigQuery cost is scan width, not row count — the same query cost 19 GB with COUNT(*) and 828 GB with SELECT *.

Validate uniqueness with the complete key. Omitting one key column makes every count look duplicated — on the journal table, dropping the ledger column produces a false 2:1 ratio that reads as production duplication.

Change 7 · correctness

Data corrections in standard products

Three corrections unrelated to Iceberg that apply to any Cortex v7 installation.

1

TIME to TIMESTAMP conversion

SAP TIME columns are not directly materializable on the Iceberg path. The conversion was applied at 145 points across 58 files.

the working formFork
CAST(column AS TIMESTAMP)                              -- not valid in BigQuery
TIMESTAMP(DATETIME(DATE '1970-01-01', column))          -- valid form

The base date is conventional and carries no meaning. The alternative — pairing each time with its corresponding date field — would require field-by-field mapping, and several fields have no date counterpart.

2

Material document key

The movements product carried 199,015 duplicate keys whose data diverged completely. They were legitimate debit/credit transfer pairs — identical quantity and date, differing only in the debit/credit indicator.

Deduplicating would have corrupted inventory balances. The fix was to add debit_credit_indicator_shkzg (SAP field SHKZG) to the uniqueKey, making each leg unique.

materials_movement/definitions/{ecc,s4}/material_documents.jsFork
publish_config.getPublishConfig(
  materializationType, tableConfig, moduleConfig,
  [
    "client_mandt",
    "document_number_mblnr",
    "document_year_mjahr",
    "document_item_zeile",
    "debit_credit_indicator_shkzg"    // <- added
  ]
);

Applied to both the ECC and S/4 definitions. This is a CREATE-time change, so it required DROP + reload. Afterward, row count and distinct key count matched exactly at 15,882,543.

3

Direct invoices in the document flow

The sales flow product modeled only the order → delivery → billing chain. Invoices issued directly from an order, with no delivery, fell outside it — understating revenue in scenarios without physical shipment.

sales_document_flow.js — beforeBaseline
-- one branch: delivery is mandatory
SELECT …
FROM vbfa AS SO
LEFT OUTER JOIN vbfa AS Deliveries
  ON SO.vbeln = Deliveries.vbelv
WHERE SO.vbtyp_n IN (delivery)
  AND Deliveries.vbtyp_n IN (billing)
-- an order billed with no delivery
-- never produces a row
sales_document_flow.js — afterFork
-- branch 1: order → delivery → billing
SELECT … FROM vbfa AS SO
LEFT OUTER JOIN vbfa AS Billing
  ON … AND Billing.vbtyp_n IN (billing)
WHERE SO.vbtyp_n IN (delivery)

UNION ALL

-- branch 2: order → billing, no delivery
SELECT … FROM vbfa AS SO
WHERE SO.vbtyp_n IN (billing)
  AND NOT EXISTS (
    SELECT 1 FROM vbfa X
    WHERE X.vbelv = SO.vbelv
      AND X.vbtyp_v IN (delivery))

The NOT EXISTS is what keeps the grain intact: branch 2 only emits rows for orders that have no delivery leg at all, so an order billed through a delivery is never counted twice.

Parameterizing bucket and connection

One codebase serves every environment. The table settings carry only the default value; at run time the pipeline injects the correct bucket and connection through Dataform's official variable mechanism.

workflow_settings.yamlFork
dataformCoreVersion: "3.0.64"   -- 3.0.59 lacks Iceberg
defaultLocation: "US"
vars:
  icebergBucket: "…-dev"
  icebergConnection: "DEFAULT"
pipeline — per-environment injectionFork
dataform run $ACTIONS_FINANCE_TX \
  --timeout=30m \
  "--vars=icebergBucket=$ICEBERG_BUCKET,\
          icebergConnection=$ICEBERG_CONNECTION" \
  --default-location $BQ_LOCATION

! Two operational traps

Do not use process.env. The Dataform sandbox does not expose it — the read fails silently and the product lands in the wrong bucket. Variables arrive through dataform.projectConfig.vars.

--timeout covers the whole run, not each action. If it expires, the final actions in the list are cut silently and the job reports success. Verify which tables actually exist after each group.

The invariants it then lists are the ones that were learned expensively: never git add .; the merge-request form pre-fills the wrong target branch; remote refs are the source of truth because local tracking refs go stale; the pipeline builds from a CI/CD file variable rather than the repository config, so registering a module locally is not enough.

! One invariant worth highlighting: the division of labor

The skill states that the agent only edits files in the working tree — it does not run builds, query BigQuery, operate the GitLab UI, or push on its own authority. The human runs those, and observed output, not predicted success, is what advances a step.

That rule exists because an agent reported a successful edit it had not made. It is worth stating explicitly in any framework that ships agent skills.

Why this might matter upstream

Cortex already treats skills as a first-class artifact, which is what made this possible. Two observations from using that system in anger:

  • The failure catalog is the valuable part. Most of what a team needs is not how the framework works when it works — it is which silent failures look like success. Several entries here (DATE(col) on a DATE column, layout configs not reaching tableConfig, orphaned GCS files after DROP) are framework behaviors, not deployment-specific ones, and would fit a framework-owned skill.
  • Skills need a place for "measure, do not assume." The strongest rules in this skill are about method — measure cost only with active CDC, never with COUNT(*), validate with the complete key. Those transfer to any deployment and are invisible in reference documentation.

✓ Available for review

Both skill files are plain Markdown in the framework's own format and can be shared as-is. The Iceberg one is written to be deployment-agnostic; the CI/CD one is specific to this customer's GitLab setup and is included mainly as an example of the shape.

  • A Cloud Storage bucket and a BigQuery cloud resource connection, registered as the project default — so one codebase serves every environment.
  • The execution service account needs storage.admin on the bucket, not just objectAdmin: BigLake sets an IAM policy when creating the managed Iceberg table.

! DROP does not clean Cloud Storage

The Parquet files and Iceberg metadata are orphaned in the bucket, and the next CREATE points at an occupied storage_uri. The prefix must be removed manually — with the trailing slash, or the prefix also matches similarly named tables.

Risks and known debt

What a team adopting this work should know before putting it into production.

High Silent duplicate from pruning

If the partition column changes value between loads, the MERGE inserts instead of updating — with no error. Safe only with a column verified immutable per key in the actual data. Detection is after the fact, through a scheduled uniqueness check.

Medium Debug line left in the helper

A conditional console.log remains, keyed on a product name. It does not affect output, but it pollutes the compile log and should be removed before wider use.

Medium Textual watermark substitution

The optimization depends on matching the subquery in the exact form Cortex generates. A formatting change upstream disables the saving without breaking anything — and without warning. Worth monitoring bytes processed after each framework upgrade.

Low Baseline drift

This deployment branched from 7.0.2 and upstream is already at 7.0.5. The longer the gap, the greater the reconciliation effort — particularly across the 46 standard products touched to adopt the helper.

Low Build artifacts in version control

The repository carries compiled output, Python caches, a virtual environment, and single-use utility scripts at the root. Nothing breaks, but it clouds the diff and makes it harder to tell deliverable from scratch work.

Note Validation gates

Compiling is not running. Several issues in this project passed YAML validation and Dataform compilation and surfaced only at execution: missing alias, non-unique key, invalid DDL.
