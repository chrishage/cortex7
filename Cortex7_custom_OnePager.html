Why we extended the framework

Cortex Framework v7 turns SAP transactional records into governed data products in BigQuery, and it does that well — the modular deployment model, dependency resolution, and incremental loading all worked as documented. Two things stood between the framework and this customer's target architecture.

First, the consumers are not all in BigQuery. A downstream lakehouse reads the same data products directly from Cloud Storage, which requires an open table format rather than native BigQuery storage. Second, at production scale the hourly incremental loads on the largest finance products were scanning far more source data than the delta justified.

We solved both without forking the deployment model: the CLI, the manifests, the annotation schema, and the module resolution are untouched. What changed is how the final table is written, and how the incremental MERGE is planned.

What we built

Three code changes carry nearly all of the value — each independent, each adoptable on its own — plus the written reasoning behind them.

1

Iceberg materialization for data products

A single include, iceberg_helper.js, emits explicit Iceberg DDL through a Dataform operations action, supporting both full-refresh and incremental products. Data products land as managed Iceberg tables in Cloud Storage, readable by external engines without export or duplication. Products that do not declare an Iceberg block fall through to the native publish() path unchanged, so adoption is per-product.

1 new include 3 lines changed per data product Backward compatible
2

Incremental watermark as a script variable

The framework's incremental filter compares source recordstamp against a correlated subquery over the target table. Because the cutoff is not known at planning time, BigQuery cannot prune partitions and reads far beyond the delta. Materializing the same value in a DECLARE before the MERGE makes it a planning-time constant. The value is identical — it is simply evaluated once.

5.5 GB → 18.6 MB on the same delta No table rebuild required
3

Partition pruning inside the MERGE

A key-only ON clause never engages the target's partitioning — BigQuery scans the full table to match keys. The helper computes the batch's date bounds into script variables and adds a range predicate as the first ON condition. On a 370-million-row product running hourly, this was the single largest saving.

612 GB → 28 GB per run Requires an immutable partition column
4

The reasoning, captured as agent skills

Cortex already ships .agents/skills/ as a first-class artifact, so we wrote what we learned in that same format: 805 lines across two phased playbooks, registered in AGENTS.md as standing rules. The larger one is a catalog of failures that look like success — each entry a symptom and a rule, drawn from a cycle that cost us real time. We think parts of it describe framework behavior, not our deployment.

What adoption looks like in a data product

The per-product change is three lines. Everything else — the SELECT, the annotations, the table settings, the manifest — stays as the framework generates it.

data product definitionv7 baseline
publish(moduleContext.moduleId + "_" + tableConfig.tableName,
        publishConfig).query(
  (ctx) => `SELECT … FROM …`
);
data product definitionWith Iceberg support
const iceberg_helper = require("includes/iceberg_helper.js");

iceberg_helper.publishProduct(
  moduleContext.moduleId + "_" + tableConfig.tableName,
  publishConfig,
  tableConfig,
  (ctx) => `SELECT … FROM …`
);

The Iceberg target itself is declared in table_settings.default.yaml, alongside the existing partition and cluster settings, and the bucket is overridden per environment through standard Dataform variables.

What we would like to discuss

We are not proposing our fork as a patch. These are the five questions we would want a product owner to weigh, in the order we think they matter.

Iceberg as a first-class materialization target design

Today, a bigquery.iceberg block in table settings passes schema validation and is silently ignored — publish() creates a native table with no warning. Whatever the roadmap decision on open table formats, this specific failure mode is worth closing: either honor the block, or reject it at build time.

The correlated subquery in the incremental filter cost

This one is independent of Iceberg and affects every incremental data product in every deployment. The fix is contained and semantically neutral. We implemented it in the helper to limit blast radius, but it arguably belongs in incremental.js, where every product would benefit. We would value your read on that.

Metadata application outside the publish() path gap

Column descriptions are applied through the Dataform API, so any product built with operations loses them entirely — annotations sit in the repository and never reach the catalog. Given that Cortex positions data products as agent-ready, metadata that silently drops on an alternate path seems worth a guard.

Partition expression generation for DATE columns bug

cortex-build emits DATE(column) from partitionType: DATE without checking the column's type. When the column is already DATE — which is the case for SAP date fields — BigQuery rejects the CREATE. We unwrap it in the helper, but the correct fix is upstream in the builder.

A home for framework failure modes in the skills docs

The most useful thing we wrote is not how the framework works — it is which silent failures look like success. Several are framework behaviors rather than ours: layout settings that pass validation and are discarded, an EXCEPTION handler that turns a metadata error into a green job, a whole-run timeout that truncates the action list and still reports success. If .agents/skills/ had a place for those, every deployment would stop rediscovering them.

! The one change that carries a correctness precondition

The range predicate makes the MERGE match only rows whose partition column falls inside the batch bounds. If that value can change between loads, the existing row falls outside the range, the MERGE misses it, and inserts a silent duplicate.

We verified immutability for posting date against 30 days of CDC and a full fiscal year before enabling it, and we monitor with a scheduled uniqueness check. If this were ever productized, we would expect it to be opt-in per data product, with the precondition stated in the documentation rather than inferred.

Also in the change set

Beyond the three headline items, the deployment produced a handful of smaller fixes to standard data products that are not specific to Iceberg or to this customer:

  • TIME to TIMESTAMP conversion at 145 points across 58 files. Note that CAST(col AS TIMESTAMP) is not valid in BigQuery; the working form is TIMESTAMP(DATETIME(DATE '1970-01-01', col)).
  • Material document key — the product had 199,015 duplicate keys that diverged completely in their data. They were legitimate debit/credit transfer pairs, identical except for the debit/credit indicator. Adding debit_credit_indicator_shkzg to the uniqueKey in materials_movement/definitions/{ecc,s4}/material_documents.js made each leg unique; deduplicating would have corrupted inventory balances.
  • Sales document flow — the product modeled only the order → delivery → billing chain, omitting invoices issued directly from an order with no delivery. Those transactions were missing from downstream revenue reporting. The fix adds a second branch under UNION ALL, guarded by NOT EXISTS so that orders billed through a delivery are not counted twice.
  • Clustering column selection — deriving cluster keys from the unique key spends slots on columns that are single-valued in many landscapes (client, ledger). Honoring the declared cluster columns recovered two of the four available slots.
